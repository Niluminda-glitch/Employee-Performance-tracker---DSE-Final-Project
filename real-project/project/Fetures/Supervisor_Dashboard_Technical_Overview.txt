🏗️ 1. TEAM MANAGEMENT SYSTEM
================================================================

FEATURE OVERVIEW:
- Hierarchical team structure management with supervisor-employee relationships
- Real-time team member status tracking and profile management
- Dynamic team composition with role-based access control

UNIQUE DIFFERENTIATORS:
- Supervisor-specific team filtering (only direct reports, not all employees)
- Real-time status updates with optimistic UI updates
- Integrated skill tracking and performance correlation
- Department-based team organization with cross-functional visibility

SYSTEM INTERACTIONS:

DATABASE SCHEMA:
- users table: id, full_name, email, role, supervisor_id, status, department_id
- departments table: id, name, supervisor_id
- user_skills table: user_id, skill_name, proficiency_level
- supervisor_teams table: supervisor_id, employee_id, assigned_date

API ENDPOINTS:
- GET /supervisor/team - Fetch direct reports
- PUT /users/{id}/status - Update employee status
- GET /users/{id}/profile - Get detailed employee profile

CLASS DIAGRAM HINTS:
Classes: SupervisorDashboard, TeamManager, Employee, Department, UserProfile
Relationships:
- SupervisorDashboard aggregates TeamManager
- TeamManager manages multiple Employee objects
- Employee belongs to Department
- Employee has UserProfile

SEQUENCE DIAGRAM HINTS:
1. Supervisor → TeamManager → Database → Employee data retrieval
2. Status Update: Supervisor → UI → API → Database → Real-time notification
3. Profile View: Supervisor → EmployeeProfileCard → API → Skills/Performance data

🔄 3. REQUEST APPROVAL WORKFLOW
================================================================

FEATURE OVERVIEW:
- Multi-type request handling (leave, overtime, general requests)
- Approval workflow with comment system
- Status tracking and history maintenance

UNIQUE DIFFERENTIATORS:
- Role-based request visibility (supervisors see only team requests)
- Bulk approval capabilities for efficiency
- Integrated comment system for approval reasoning
- Real-time status updates to requesters
- Request type filtering and categorization

SYSTEM INTERACTIONS:

DATABASE SCHEMA:
- requests table: id, user_id, type, start_date, end_date, reason, status, created_at
- request_approvals table: request_id, approver_id, status, comments, approved_at
- overtime_requests table: request_id, hours_requested, justification
- leave_requests table: request_id, leave_type, emergency_contact

API ENDPOINTS:
- GET /requests/team - Fetch team requests for supervisor
- PUT /requests/{id}/approve - Approve request
- PUT /requests/{id}/reject - Reject request with comments
- GET /requests/{id}/history - Get approval history

WORKFLOW STATES:
pending → approved/rejected → completed (for leave) / processed (for overtime)

CLASS DIAGRAM HINTS:
Classes: RequestManager, Request, LeaveRequest, OvertimeRequest, ApprovalWorkflow
Relationships:
- RequestManager handles multiple Request types
- LeaveRequest and OvertimeRequest extend Request
- ApprovalWorkflow manages request state transitions
- Request has relationship with User (requester) and User (approver)

SEQUENCE DIAGRAM HINTS:
1. Request Approval: Supervisor → RequestCard → ApprovalDialog → API → Database → Employee Notification
2. Bulk Approval: Supervisor → RequestList → BulkActions → API → Multiple Database Updates
3. Request History: Supervisor → RequestDetails → API → ApprovalHistory → Display

UNIQUE DIFFERENTIATORS:

NOTIFICATION TYPES:

Classes: NotificationManager, Notification, Recipient, NotificationChannel, Department
Relationships:
- NotificationManager creates Notification
- Notification has multiple Recipient objects
- Recipient links to User
- NotificationChannel handles delivery methods

SEQUENCE DIAGRAM HINTS:
1. Notification Creation: Supervisor → CreateNotificationModal → RecipientSelector → API → Database → DeliveryService

🔐 8. AUTHENTICATION & AUTHORIZATION FRAMEWORK
================================================================

FEATURE OVERVIEW:
- Role-based access control with granular permissions
- Google OAuth integration with Supabase
- Session management and security

UNIQUE DIFFERENTIATORS:
- Hierarchical role system (employee → supervisor → manager)
- Feature-level permission control
- Secure API endpoint protection
- Session timeout and refresh handling

SYSTEM INTERACTIONS:

AUTHENTICATION FLOW:
1. Google OAuth → Token Exchange → Supabase Auth → Role Assignment
2. JWT Token → API Middleware → Permission Check → Resource Access
3. Session Refresh → Token Renewal → Continued Access

AUTHORIZATION LEVELS:
- supervisor: Can manage direct reports only
- manager: Can manage all employees
- employee: Can view own data only

CLASS DIAGRAM HINTS:
Classes: AuthManager, PermissionChecker, RoleValidator, SessionManager, SecurityMiddleware
Relationships:
- AuthManager handles authentication flow
- PermissionChecker validates access rights
- RoleValidator ensures proper role assignment
- SecurityMiddleware protects API endpoints

SEQUENCE DIAGRAM HINTS:
1. Login: User → Google OAuth → Supabase → Role Assignment → Dashboard Access
2. API Access: Request → SecurityMiddleware → PermissionCheck → Resource Access
3. Session Refresh: Token Expiry → RefreshToken → New Session → Continued Access

   Key Relationships:

   Classes: RequestManager, Request, LeaveRequest, OvertimeRequest, ApprovalWorkflow, Approver
   Key Relationships:
   - LeaveRequest and OvertimeRequest extend Request (inheritance)
   - ApprovalWorkflow manages Request state transitions
   - Approver processes Request approvals
   - RequestManager coordinates workflow

4. **NOTIFICATION BROADCASTING SYSTEM**
   Classes: NotificationManager, Notification, Recipient, NotificationChannel, Department
   Key Relationships:
   - NotificationManager creates Notification instances
   - Notification has multiple Recipients (one-to-many)
   - NotificationChannel handles delivery methods
   - Department groups Recipients

5. **TEAM MANAGEMENT SYSTEM**
   Classes: TeamManager, Employee, Supervisor, Department, EmployeeProfile, Skill
   Key Relationships:
   - Supervisor manages multiple Employees (one-to-many)
   - Employee belongs to Department
   - Employee has EmployeeProfile (composition)
   - EmployeeProfile contains Skills (aggregation)
